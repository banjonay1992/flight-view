# The maths

Everything here is implemented three times (Python reference, Swift, Kotlin), and the two app implementations are tested against fixtures generated by the reference. The reference itself is checked against pymap3d to 1e-7 degrees over 500 random cases.

## Frames

- **Geodetic**: latitude, longitude, height above the WGS84 ellipsoid (HAE).
- **ECEF**: Earth-centred, Earth-fixed Cartesian metres.
- **ENU**: local east, north, up at the observer.
- **Device**: +X to the right of the screen, +Y to the top, +Z out of the screen towards the user. The rear camera looks along -Z. Both apps are locked to portrait, so this is the same on iOS and Android.

A device attitude is the 3x3 matrix `R_dw` that maps a device-frame vector to ENU: `w = R_dw d`.

## Heights

ADS-B geometric altitude (`alt_geom`) is GNSS height above the ellipsoid. iOS `CLLocation.ellipsoidalAltitude` and Android `Location.getAltitude()` are also ellipsoidal, so observer and aircraft share one vertical datum. We prefer geometric altitude over barometric (`alt_baro`), which is pressure altitude against a standard atmosphere and can be off by several hundred feet. Using mean-sea-level height for the observer would add the geoid separation (about 50 m in Cornwall, up to 100 m elsewhere).

## Look angles

Geodetic to ECEF with WGS84 (a = 6378137 m, f = 1/298.257223563). Difference the two ECEF points and rotate into ENU at the observer:

```
e = -sin(lon) dx + cos(lon) dy
n = -sin(lat) cos(lon) dx - sin(lat) sin(lon) dy + cos(lat) dz
u =  cos(lat) cos(lon) dx + cos(lat) sin(lon) dy + sin(lat) dz
azimuth   = atan2(e, n)
elevation = atan2(u, sqrt(e^2 + n^2))
```

This handles Earth curvature exactly: an aircraft at 35,000 ft 150 km away sits 3.4 degrees above the horizon, not the 4.1 degrees a flat-Earth calculation gives. That 0.7 degree error would put the label several aircraft-lengths off on a zoomed-in phone. We deliberately do not apply astronomical refraction. It assumes the light crosses the whole atmosphere, which overstates the effect for a target inside it, and above 5 degrees elevation the real correction is under 0.1 degrees, well below compass error.

## Dead reckoning

Each report carries the time the position was measured. On every frame we advance it to "now" on the server's clock (the phone measures its clock offset from each response, so a wrong phone clock doesn't matter):

```
d     = ground_speed * dt / R
lat2  = asin(sin lat1 cos d + cos lat1 sin d cos track)
lon2  = lon1 + atan2(sin track sin d cos lat1, cos d - sin lat1 sin lat2)
h2    = h1 + vertical_rate * dt
```

`dt` is clamped to 60 s. Reports older than 30 s are drawn faded, and older than 120 s are dropped.

## Attitude

**Android**: `TYPE_ROTATION_VECTOR` through `getRotationMatrixFromVector` gives device to (east, magnetic north, up). We rotate about the vertical by the local magnetic declination from `GeomagneticField` (the World Magnetic Model) to get true north. The rotation that adds D degrees to every azimuth is:

```
Rz(D) = [ cos D   sin D   0 ]
        [-sin D   cos D   0 ]
        [   0       0     1 ]      R_dw(true) = Rz(D) R_dw(magnetic)
```

**iOS**: CoreMotion's `.xTrueNorthZVertical` frame is already true north, with axes (north, west, up). We map it to ENU with `e = -y, n = x, u = z`. Apple's documentation is loose about whether `rotationMatrix` maps device to reference or the reverse, and getting it backwards mirrors every label. So `AttitudeResolver` checks both against gravity, which CoreMotion reports in device coordinates. The correct matrix maps "up in the device frame" (minus gravity) onto reference +Z. It decides once, with a margin, and caches the answer.

**Manual nudge**: phone compasses are often a few degrees out near metal or electronics. In calibration mode the user drags the sky until a visible plane sits under its label. That offset is applied with the same `Rz` and saved.

## Projection

For a unit ENU direction `w`, the device-frame vector is `d = R_dw^T w`. The camera looks along -Z, so depth is `z = -d.z`. If `z <= 0` the target is behind the camera. Otherwise:

```
x = cx + f * d.x / z
y = cy - f * d.y / z        (screen y grows downwards)
```

The focal length comes from the camera itself. iOS gives `videoFieldOfView` for the active format; on Android we compute it from the sensor's physical size and focal length, allowing for the crop when the stream's aspect differs from the sensor's. In portrait the long side of the image is vertical. The preview aspect-fills the view, scaling the image by `s = max(viewW / 1, viewH / aspect)` in units where the image is `1 x aspect`, so

```
f = (aspect / 2) / tan(longSideFov / 2) * s
```

The fixture `test_projection_edge_matches_fov` checks that an aircraft exactly half the field of view above the camera axis lands exactly on the top edge of the screen.

For aircraft off screen we draw an arrow at the edge in the direction `atan2(d.y, d.x)`, which works for targets behind you too.

## Smoothing and declutter

Sensor jitter is far more visible than a few frames of lag, so screen positions get exponential smoothing with a 120 ms time constant. A jump of more than 160 points snaps immediately, so labels never trail across the screen when you swing the phone.

Labels are placed nearest aircraft first. Each tries a short list of slots (directly above, stacked above, below, then further out) and takes the first that does not overlap a placed label. If none fit, the aircraft keeps its dot without a label. At most 14 labels are shown.
